* The decision
**We do not widen what catherine can express.** We make the three axes it
already serves honest and enforceable, and we leave the constraint language
where it is.

Concretely: five small items (one payload, one parser refusal, one reuse, one
hint, one registry cell), one optional repository asset (the architecture
policy gate), and a set of documentation corrections that cost nothing but
change what the project claims about itself.

The reason is the review's own evidence: the differentiator that is real and
hard to copy is not a feature list — it is that catherine's *limits* are
executable (14 registry rows, 8 open / 6 closed, each with a live case and a CI
gate). Widening the language dilutes the thing that is already distinctive;
tightening the honesty of the existing axes strengthens it.

* The three axes (and the gate they form)
| Axis | What it means | What serves it | Done when |
|---|---|---|---|
| **A — referential agreement** | claims of the form "these two stored paths must land on the same row" | path equations, keys, coproducts, pullbacks, naturality, composition | every such claim the model states is executed with a witness; what cannot be stated is named in a registry row |
| **B — schema evolution** | what a schema change does to the data | ~migrate~ (Δ), ~diff~, the schema-map parser | no change can silently produce a wrong instance or a lost constraint |
| **C — executable limits** | knowing and proving what the tool cannot do | the expressibility registry, the gap suite, the negative-control bundles | every limitation claim names a registry row and a live case; a stale row fails CI |

**The gate:** a proposed capability that serves none of A, B or C is refused by
default. This is the treatment the rule lens already received (a
pre-registered hypothesis, scoped to extracted tables only) — the gate is the
repo's own practice, written down.

* "State-shape domain" — defined once
> A domain whose claims are about the *shape and agreement of stored
> references* — which rows exist, which references they carry, and which
> composed paths must agree — rather than about computation over values
> (arithmetic, time, decisions over data).

Rule of thumb: if the claim can be written as "these two stored paths must land
on the same row", it is in scope (axis A); if it is about *evolution*, it is
axis B; if it is about *values, time or cardinality*, it is out of scope and
belongs in the registry as a named gap (axis C). This definition replaces the
eleven uses of "state-shape" that had no definition (review finding CLAR-001).

* Done-when (the stopping rule)
The programme above is finished when: Phase 0's documentation corrections are
landed; items 5–8 have landed; the registry rows that the landed capabilities
close are ~closed~ with sealing evidence and the others are still ~gap~ and say
why; ~catherine check~ reports its execution scope so "clean" is
distinguishable from "unchecked"; and the architecture gate (if Phase 3 lands)
has its policy, its extractor test and its negative-control bundle.

Beyond that the backlog does not grow by default: a new item must name the axis
it serves or be refused.

* Not doing (and why)
| Refused | Reason |
|---|---|
| identity path form | a working workaround exists in the shipped katas (identity laws stated as fixed-point over a concrete arrow); equational algebra is the classic route to a generic checker |
| cardinality / existence predicates | real state-shape claims, but they widen the constraint language toward a constraint solver — admissible only after the state-shape definition lands, and then only with a triviality-floor test |
| a general value / multi-valued-cell type | that is a data model, not a kernel |
| default row bounds for ~search~/~diff~ | a hint naming the bound to pass is enough; deriving bounds from the instance would change what "within bounds" means |
| "model this conventionally" as a new finding kind | the honest verdict belongs in the ~hints~ channel, not in a new exit class |
